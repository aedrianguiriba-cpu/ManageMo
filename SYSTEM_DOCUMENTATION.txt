OVERVIEW
--------
ManageMo is a web-based inventory and asset management system built for
Pampanga State University (PSU), plus a companion Flutter mobile app for
confirming deliveries by QR code.

The web app runs on PHP (no framework) using Bootstrap 5.3 and Font Awesome 6.4.
All pages are server-rendered PHP. Session-based authentication (BCrypt passwords).

Persistence is a REAL Supabase (hosted Postgres + PostgREST) database — this is
NOT a hardcoded/mock-data system. All reads/writes (requests, inventory, users,
borrow records, condemnation, etc.) go through the REST API and are durable
across requests. Data access lives in:
  config/data.php                — data-layer functions (getUsers, getInventory,
                                    getRequests, ...) backed by Supabase REST calls,
                                    with a short-lived in-process cache (60s TTL)
  config/supabase.php             — thin PostgREST HTTP client (select/insert/
                                     update/delete) + .env loader
  config/mock_data.php            — legacy MockData class kept for reference only;
                                     NOT called anywhere in the current codebase
  config/functions.php            — business logic helpers (auth, QR generation,
                                     email, dbCreate*/dbUpdate*/dbDelete* wrappers)
  config/constants.php            — app-wide constants (roles, statuses, urgency)
  config/departments_custom.json  — LEGACY, unused (see KNOWN LIMITATIONS) —
                                     colleges/offices/campuses now live in the
                                     Supabase `departments` table instead
  .env                             — SUPABASE_URL, SUPABASE_KEY (service_role),
                                     API_TOKEN_SECRET (used by api/*.php)

  app_settings table (Supabase)   — key/value store for site-wide admin
                                     settings (terminology mode, borrow
                                     catalog page size). Read/written via
                                     getAppSettings()/getAppSetting()/
                                     setAppSetting() in config/data.php.
                                     Must be created manually via the SQL in
                                     database/schema.sql — it is not created
                                     automatically. See Module 15b.

────────────────────────────────────────────────────────────────────────────────
MODULE 1: AUTHENTICATION  (index.php, auth.php, logout.php)
────────────────────────────────────────────────────────────────────────────────
Flow:
  1. User visits index.php — shown split-panel login form (email + password).
     Left panel: storagebg.jpg with blurred backdrop + maroon gradient overlay.
     Right panel: white form panel with logo, inputs, remember me, forgot password.
  2. Form POSTs to index.php (self-posting).
  3. PHP calls getUsers(), finds user by email, verifies BCrypt hash via
     password_verify(). On success: sets $_SESSION['user_id'], redirects to
     role-appropriate dashboard (/admin/dashboard.php or /user/dashboard.php).
  4. Forgot Password form toggles in-place via showForgot()/showLogin() JS.
     No actual email is sent — placeholder success message shown.
  5. logout.php calls session_destroy(), redirects to index.php.

Role system:
  ROLE_ADMIN = 'admin'  → admin/ pages only
  ROLE_USER  = 'user'   → user/ pages only
  requireAdmin() / requireUser() guard every page and redirect if role mismatch.

Security:
  - Passwords hashed with BCrypt (PASSWORD_BCRYPT / $2y$ hashes).
  - All user-supplied values passed through sanitizeInput() (htmlspecialchars + trim).
  - The mobile app verifies the SAME bcrypt hash client-side with Dart's `bcrypt`
    package — confirmed cross-compatible with PHP's password_hash() output.

────────────────────────────────────────────────────────────────────────────────
MODULE 2: INVENTORY  (user/inventory.php, admin/inventory.php, admin/inventory-campus.php)
────────────────────────────────────────────────────────────────────────────────
Data source: getInventory() → array of items (live Supabase `inventory` table).
Each item has:
  id, qr_code_id, item_name, category, description, college_id, quantity,
  status, location, purchase_date, cost, condition, condemnation_reason,
  condemned_at, condemned_by, condemned_condition, disposal_notes,
  disposed_at, disposed_by, group_id, acquisition_mode, model,
  serial_number, created_at
  (campus_id was dropped from this table — see this module's note below and
  the ERD's caption.)

Item statuses: available | borrowed | maintenance | damaged | requested | condemned | disposed

QR Code system:
  - Every inventory row has its own qr_code_id (e.g. 'QR-A1B2C3D4E5...'), one
    physical unit per row (adding N units = N inventory rows, not one row with
    quantity=N and per-unit suffixes).
  - lib/qrcode.php generates the actual QR image for each code.
  - QR images are stored in assets/qrcodes/.

User view:  read-only browse (Available/Borrowed tabs) + "Department Owned
            Items" tab, all paginated (ITEMS_PER_PAGE=15 groups per page).
            The owned-items tab is scoped to the viewer's whole department
            (see Module 2b) and, when department sharing is active, adds a
            filter card with Search, Category, and Owner dropdowns — same
            .inv-filter-card pattern used by the other tabs, with an
            "Owner" column shown on each item card whenever more than one
            account shares the pool.
Admin view: add items, add units to an existing item, edit item details/status,
            view a per-item detail modal with each unit's QR code.
            Deletion has been REMOVED — there is no way to delete an inventory
            item from the admin UI or its POST handler anymore. To retire an
            item, use the Condemnation & Disposal flow (Module 9) instead.
Campus view (admin/inventory-campus.php):
  - Grid of all campus cards with per-campus stats.
  - Main Campus card shows Colleges and Offices breakdowns.
  - "Manage Departments" button opens a tabbed modal (see Module 12).

────────────────────────────────────────────────────────────────────────────────
MODULE 2b: DEPARTMENT DATA SHARING  (config/functions.php, mirrored in mobile app)
────────────────────────────────────────────────────────────────────────────────
Accounts that share the same college_id are treated as one pool: owned items,
borrow records, and request history are fully shared and actionable across
every account in that college — not just visible, but the same data surface
each member's own actions would use.

Core helper:
  getDepartmentMateIds(array $user): array
    - Returns every user ID sharing $user['college_id'].
    - If the user has NO college_id set, returns [$user['id']] only — i.e.
      unassigned accounts are NEVER pooled with each other. This is a
      deliberate privacy-safe default (not user-specified) so that accounts
      without a department don't accidentally see each other's data.
  Mirrored in the mobile app as _departmentMateIds()/_idsFilter() in
  mobile_app/lib/services/api_client.dart, used to scope pending/completed
  deliveries and the item-lookup feature the same way.

Applied throughout:
  - user/inventory.php    — Department Owned Items tab, "already borrowed" checks
  - user/requests.php     — availability/ownership checks
  - user/my-requests.php  — request list + stats
  - user/borrow-records.php — all 3 record tables ("Borrowed By"/"Requested By"
    owner column shown whenever count($dept_user_ids) > 1)
  - user/dashboard.php    — KPIs, Return Schedule Calendar, Owned Items widget
  - user/settings.php     — profile sidebar activity stats
  - mobile_app            — pending/completed deliveries, item lookup

UI convention: pages compute `$show_owner_col = count($dept_user_ids) > 1;`
and only render an Owner/Borrowed-By/Requested-By column or filter when true,
so a solo (no-department) account sees the exact same single-user UI as
before this feature existed.

────────────────────────────────────────────────────────────────────────────────
MODULE 3: REQUEST SUBMISSION  (user/requests.php)
────────────────────────────────────────────────────────────────────────────────
Three request types (selected via type cards at the top):
  a) Borrow   — borrow an existing inventory item temporarily (catalog-only —
                see "Custom items" below)
  b) Item     — request procurement of a new item (catalog OR custom name)
  c) Service  — request maintenance/repair/service on an existing item

Form fields (vary by type):
  Borrow:  item (shop grid, catalog only), quantity, expected return date,
           urgency, reason
  Item:    item (shop grid, catalog OR "Other/Custom" with a free-text name),
           description, quantity, urgency, reason
  Service: item (shop grid), service type, description, urgency

Page layout: two-column (.rq-layout) — form card (left) + request summary
sidebar (right, 300px). Collapses to single column at ≤900px.

Custom items ("Item" request type only):
  - The Borrow flow's "Other (custom)" option has been removed — users can only
    borrow items that already exist in the catalog.
  - For an Item request with no catalog match, NO inventory row is created at
    submission time. The custom name is stashed in the request's
    service_description column so it still displays correctly everywhere
    (my-requests.php, admin/requests.php list + detail views) while pending.
  - An inventory row for the custom item is created ONLY when an admin approves
    the request (admin/requests.php's approve handler) — category defaults to
    "Other", campus = the requester's campus, condition defaults to "good"
    (a missing condition previously broke the admin item-detail modal's JS).
    The new inventory_id is then written back onto the request row so it's
    "counted" in inventory going forward.
  - Disapproved/still-pending custom item requests never get an inventory row.

Server-side:
  - Each unit of a submitted request becomes its own row in `requests` (one
    row = one physical unit), sharing a `group_id` across the whole submission
    so multi-unit requests can be tracked/approved/delivered together.
  - dbCreateRequest() / dbUpdateRequest() / dbUpdateInventory() persist directly
    to Supabase — nothing here is session-mocked.

────────────────────────────────
SHOP-STYLE ITEM SELECTION GRIDS
────────────────────────────────
All three request types use a shop-style card grid for item selection instead
of a plain <select> dropdown. Each grid has:
  - A hidden <select> (original ID kept for JS compatibility with handleCatalogChange,
    addToCart, updateSummary, resetStaging)
  - A search input (live filter)
  - Category filter pills (horizontal scrolling, wraps on mobile)
  - A card grid

Grid 1 — Borrow (#bshop-grid, $borrow_catalog):
  Includes available AND borrowed items. Cards display:
    - Category icon + color strip (.bshop-icon)
    - Item name (.bshop-name)
    - Location chip (.bshop-loc)
    - Availability badge: "Available (qty)" green or "X borrowed" amber
    - Expected return date pills (one per active borrow record, sorted asc)
    - Unit price + status pill in footer
  Catalog-only — no "Other/Custom" card (removed).
  selectBorrowCard() / filterShopItems() handle selection & filtering.
  data-item-id, data-status, data-quantity, data-available on each card.
  Category filter: filterShopItems(btn) toggles .bshop-cat.active.

Grid 2 — Item Request (#ishop-grid, $catalog_by_category):
  Available-only items, PLUS an "Other / Custom" card (see "Custom items" above).
  selectItemReqCard() / filterItemShop() handle selection & filtering.

Grid 3 — Service (#sshop-grid, $inventory_items):
  All campus items regardless of status. Status-colored badge per item.
  selectServiceCard() / filterServiceShop() handle selection & filtering.

JS function resetStaging() clears all three grids on request type switch.

Category color map ($catMeta in PHP, reused in all three grids):
  Electronics      icon fa-laptop             color #1e40af  bg #dbeafe
  Furniture        icon fa-chair              color #92400e  bg #fef3c7
  Equipment        icon fa-screwdriver-wrench color #166534  bg #dcfce7
  Supplies         icon fa-boxes-stacked      color #6b21a8  bg #f3e8ff
  Appliances       icon fa-plug               color #0f766e  bg #ccfbf1
  Security         icon fa-shield-halved      color #9f1239  bg #ffe4e6
  Office Equipment icon fa-print              color #0369a1  bg #e0f2fe
  (default)        icon fa-box                color #6b7280  bg #f3f4f6

PHP data ($borrow_catalog):
  - Includes BOTH available and borrowed items (not just available).
  - Items grouped by category.
  - $item_avail_data maps inventory_id → array of active borrow records,
    each with { return_date, is_overdue }. Multiple records exist when multiple
    units of the same item are borrowed simultaneously.

Quantity cap:
  - handleCatalogChange() reads data-available from the selected card/option
    and sets the quantity input's max attribute to (total qty − borrowed count).
  - If the current value exceeds the new max it is automatically clamped down.
  - Tooltip on the input shows "Maximum available: N".

MODULE 4: REQUEST MANAGEMENT / APPROVAL  (admin/requests.php)
────────────────────────────────────────────────────────────────────────────────
Data source: getRequests() → array of all requests (live Supabase `requests` table).
Each request row has:
  id, request_number, user_id, group_id, qr_code_id, request_type (borrow/item/
  service), inventory_id (nullable — see Module 3's "Custom items"),
  service_description, urgency (low/medium/high/critical), receiving_method,
  reason_for_request, expected_return_date, quantity_requested, status,
  delivery_status, approved_by, approved_at, created_at, updated_at

Request lifecycle:
  pending → approved / disapproved → (approved) → out_for_delivery → delivered
                                                                    → (borrow) returned

Admin actions (grouped — one action applies to every unit sharing a group_id):
  - Filter by type, status, urgency, campus; table view or tracker (stepper) view.
  - Approve → status='approved'. If the request has no inventory_id (a custom
    item — see Module 3), an inventory row is created for it HERE and linked
    back onto the request before the status change is applied.
  - Disapprove with reason → status='disapproved'; releases any reserved
    inventory unit back to 'available'.
  - Mark Out for Delivery → delivery_status='out_for_delivery' (+ email).
  - Mark Delivered → delivery_status='delivered', status='delivered'; for borrow
    requests, flips the inventory unit to 'borrowed' and creates a borrow_record.
    (The mobile app's QR scan performs this same update per-unit instead of the
    admin doing it manually — see Module 13.)

Item name display:
  - The item/service name is resolved from the linked inventory row, falling
    back to service_description (covers custom items and legacy rows with no
    request_items match) before finally falling back to "N/A"/"Unknown Item".
  - Shown in: the dedicated Item/Service tab tables, the "All" tab's table view
    (added "Item" column), and the tracker card view (added under the
    requester's name).

Email notifications:
  sendDeliveryEmail($email, $name, $request_number, $stage)
    stages: 'out_for_delivery' | 'pickup_ready'
  Uses PHP mail() — requires a working SMTP/sendmail config.

MODULE 5: MY RECORDS  (user/borrow-records.php)
────────────────────────────────────────────────────────────────────────────────
Three tabs via ?tab=borrow|item|service (default: borrow).
Status filter per tab via ?status= (hidden input preserves tab on form submit).
Each tab is paginated independently at 10 rows/page (shared `page` query param —
safe because only one tab's table is ever rendered per request).

Tab 1 — Borrow Records:
  Source: getBorrowRecords() filtered by user_id, plus any borrow requests not
  yet delivered (shown as "in progress" rows with no borrow_records entry yet).
  Columns: Item, Borrowed, Expected Return, Returned On, Status, Notes.
  Status badges: active (blue) | returned (green) | overdue (red) | pending (amber).
  Overdue detection: active record where expected_return_date < now().

Tab 2 — Item Requests:
  Source: getRequests() filtered by user_id + request_type='item'.
  Columns: Request #, Item/Description, Urgency, Reason, Submitted, Status.

Tab 3 — Service Requests:
  Source: getRequests() filtered by user_id + request_type='service'.
  Columns: Request #, Item, Service Type, Description, Urgency, Submitted, Status.

Print: window.print() — @media print hides sidebar/topbar/tabs/filters/pagination.

Paginated at 5 cards per page, with prev/next + numbered page links and a

MODULE 8: BORROW MANAGEMENT  (implicit via borrow-records + admin/requests)
────────────────────────────────────────────────────────────────────────────────
Data source: getBorrowRecords() → array of borrow tracking records.
Each record has:
  id, inventory_id, user_id, request_id,
  borrow_date, expected_return_date, actual_return_date (null until returned),
  status (active/returned/overdue), notes, created_at

Overdue logic: status='active' AND expected_return_date < today.
Return process: admin sets actual_return_date → status = 'returned' →
                inventory item status reverts to 'available'.
Delivery confirmation (creates the borrow_record in the first place):
  either the admin's "Mark Delivered" action, or the requester scanning the
  unit's QR code in the mobile app (Module 13) — both run the same logic.

Multi-unit borrows:
  A single item (e.g. one item_name with 5 inventory rows) may have multiple
  simultaneous active borrow records — one per borrowed unit. The borrowed
  count = number of active records for that item's inventory rows. Available
  count = total units − borrowed count.

Accessed via "Manage Departments" button on the Campus Inventory page.

MODULE 13: QR DELIVERY SCANNER  (mobile_app/ — Flutter app, IMPLEMENTED)
────────────────────────────────────────────────────────────────────────────────
A companion Flutter app that lets a user scan the QR code on a delivered item
to confirm receipt, instead of an admin manually clicking "Mark Delivered".

Architecture (IMPORTANT — read before extending this app):
  The app talks DIRECTLY to Supabase's PostgREST API using the SAME
  SUPABASE_KEY as the web app's .env — which is the service_role key. This
  key bypasses Row Level Security entirely and grants full read/write access
  to every table in the database.

  This was a deliberate, explicitly-confirmed tradeoff (the user chose this
  over a safer anon-key + Postgres-RPC design, and over routing through the
  api/*.php backend) — see mobile_app/lib/services/supabase_config.dart for
  the in-code warning. Practical consequence: anyone who installs/decompiles
  this app can extract the key and get full database access. If this app is
  ever distributed beyond a trusted/internal audience, this should be revisited
  — either move back to the api/*.php endpoints (key stays server-side only)
  or swap to a restricted anon key + RLS policies / SECURITY DEFINER RPCs.

  The api/*.php endpoints (Module "API" in the directory tree) already implement
  the safer alternative (stateless signed tokens, password check + all writes
  happen server-side) but are currently unused by the shipped app.

Login:
  - Same accounts as the web app (users.email / users.password).
  - App fetches the `users` row by email via PostgREST, then verifies the
    password with the `bcrypt` Dart package against the stored $2y$ bcrypt
    hash — confirmed byte-for-byte compatible with PHP's password_hash().
  - No password ever leaves the device in plaintext; only the fetched hash is
    compared locally. Session = the logged-in user's profile cached in
    SharedPreferences (there is no separate token — the embedded API key
    itself is what actually grants backend access).

Home screen — two tabs:
  - "Pending Scan": this user's requests with delivery_status='out_for_delivery',
    grouped by group_id (one card per request, showing item name(s) + unit count).
    Tapping a card opens the scanner SCOPED to that item (no generic scan button —
    the user must pick the item first).
  - "Completed": this user's delivery_status='delivered' requests, most recent first.
  Pull-to-refresh reloads both tabs.

Scanning flow (per-unit confirmation):
  - Only QR codes belonging to the SELECTED item's request/group are accepted;
    scanning an unrelated QR is rejected ("This QR code belongs to a different
    item...") rather than silently confirming the wrong thing.
  - Multi-unit requests are confirmed ONE QR AT A TIME — scanning one unit's
    QR does NOT auto-confirm the whole group. The scanner stays open between
    scans, shows a running "confirmed X of Y" progress banner, and prompts for
    the next unit's QR.
  - When the last unit of the selected item is confirmed, the scanner
    auto-closes (after a short delay) with a summary; the user can also tap
    "Done" at any time to leave early.
  - Confirming a unit mirrors admin/requests.php's "Mark Delivered" action:
    sets delivery_status/status='delivered' on that request row, and — for
    borrow-type requests — flips the inventory unit to 'borrowed' and inserts
    a borrow_records row.

QR Code format: whatever qr_code_id was generated for that inventory row /
request unit (see Module 2) — matched via an exact `qr_code_id=eq.` lookup,
no special per-unit suffix parsing needed.

"Check Item Details" (read-only lookup, item_lookup_screen.dart):
  - Reached from the home screen's "Scan" nav button — separate from, and
    does not switch into, the delivery-confirmation scanner.
  - Scans any inventory item's QR code and shows its details (name, category,
    status, location, condition, owner, etc.) via api_client.dart's
    lookupItemDetails(), which is department-scoped the same way as the rest
    of the app (Module 2b).
  - Purely read-only — makes no writes to Supabase, unlike scanner_screen.dart.

Duplicate/stale-scan handling (scanner_screen.dart + confirmDelivery()):
  - A `_confirmedCodes` set in scanner_screen.dart ignores the camera
    re-firing a stale detection right after a scan (prevents a spurious
    "already confirmed" error on the unit just scanned).
  - confirmDelivery() in api_client.dart filters matches to
    delivery_status=out_for_delivery FIRST, so a reused/recycled QR code
    can't match a stale historical (already-delivered) request row from a
    previous borrow cycle.
  - confirmDelivery() writes the ORIGINAL REQUESTER's user_id (not the
    scanning user's) into the borrow_records/notifications rows it creates —
    important once department-mates can scan for each other under Module 2b.

Build/verify notes: `flutter analyze`, `flutter test`, and `flutter build apk`
all pass. Requires the CAMERA permission (wired into AndroidManifest.xml /
Info.plist's NSCameraUsageDescription).

KNOWN LIMITATIONS / OPERATIONAL NOTES
================================================================================

  - Inventory items cannot be deleted from the admin UI by design (Module 2) —
    use Condemnation & Disposal to retire an item instead.
  - Custom item requests submitted BEFORE the service_description fallback was
    added have no recoverable name (it was never persisted anywhere) and will
    still show "N/A"/"Custom Request". New submissions do not have this issue.
  - Email delivery (approval/out-for-delivery notices) requires a working PHP
    mail() / SMTP configuration — not verified/configured in this environment.
  - QR scanning in the mobile app requires camera permission and a physical/
    emulated camera; the emulator's virtual camera can scan codes shown on
    another screen or via its "extended controls" camera image injection.
  - SECURITY: the Flutter app embeds the Supabase service_role key directly
    (see Module 13) — this is a known, explicitly-accepted risk for the
    current trusted/internal deployment, not an oversight. Revisit before any
    wider distribution of the app.
  - config/mock_data.php is legacy/dead code — no longer referenced anywhere;
    kept only as a historical reference for the original data shape.
  - config/departments_custom.json is ALSO legacy/dead code — departments
    (colleges/offices/campuses) migrated to a real Supabase `departments`
    table (Module 12); nothing reads or writes the JSON file anymore.
  - The app_settings table (Module 15b) is not created automatically — it
    must be created manually in the Supabase SQL editor using the DDL in
    database/schema.sql before the Terminology switch or Borrow Catalog
    page-size setting will work; until then, those features will error/no-op.
  - Department data sharing (Module 2b) pools by college_id only. Since
    college_id can hold a college, office, or campus abbreviation
    interchangeably (Module 12), pooling in practice follows whichever of
    those three the user's college_id happens to be set to.
